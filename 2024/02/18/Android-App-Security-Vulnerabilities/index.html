Android APP常见安全漏洞

Android 安全笔记如果只列漏洞名，很容易变成一张越来越长的清单。实际审计时更有用的是沿着一条输入往下追：谁能提供它，经过什么权限检查，最后触发了什么操作。

下面从四大组件、网络、WebView、数据存储和 ZIP 解压几个方向追踪输入边界，并补上版本条件、代码审查位置与验证方法。文中的 Java/XML 用于解释边界，不是一套已经在所有系统版本上跑过的完整 App；实际测试应同时记录 Android 版本、targetSdkVersion、WebView 版本和 APK 构建类型。

概述：从入口跟到敏感操作

导出组件、URL、文件名、JSON 字段都是输入入口。风险是否成立，要看这条路径能否跨过原本应该存在的限制。例如导出 Activity 可能只是合法分享入口，也可能绕过首页登录直接进入敏感操作；这需要继续读代码和验证行为。

入口 优先追踪的数据 可能到达的位置
Activity / Deep Link URI、extras、嵌套 Intent 页面、支付或账户操作、WebView
Service / Binder 方法参数、调用 UID 文件操作、设备能力、后台任务
Provider URI、projection、selection、文件模式 数据库、私有文件
Receiver action、extras、发送方条件 状态修改、任务触发
网络 / 本地端口 请求身份、消息格式、资源 ID 业务数据、命令处理

先把版本条件写清楚

检查点 需要记录的条件
Manifest 组件导出 Android 12 上，target 31+ 且带 intent-filter 的 Activity、Service、Receiver 需要显式声明 android:exported
动态 Receiver Android 14 上，target 34+ 的相关注册需要声明 EXPORTED/NOT_EXPORTED；仅接收系统广播有例外
WebView 文件访问默认值 setAllowFileAccess 的默认值与 target SDK 有关，target 30+ 为 false，较低 target 为 true
网络信任与明文策略 同时检查 target SDK、Network Security Config 和具体网络库是否遵守相应策略
备份 区分云备份、设备间迁移、旧 adb backup 流程，检查所用系统与备份规则

这些是定位常见旧笔记问题的边界，不是完整 Android 行为变更表。对应说明分别见 Android 12、Android 14、WebSettings。旧版本漏洞仍有研究价值，但需要注明其成立环境。

四大组件

Activity：能打开页面之后，还能做什么

先看合并后的 Manifest，而不是只看源码里某一个 manifest 文件。记录 exported、permission、intent-filter、deep link 与任务栈相关配置，再跟进 onCreate、onNewIntent 以及最终的业务动作。

最小验证过程可以是：在测试 App 的未登录状态下，用外部调用者打开目标组件，观察是否仍检查会话、能否读到数据、能否完成敏感操作。只显示一个空白 Activity，与实际读取别人的订单，是不同的影响。

Service：线程与权限是两回事

Service 不自动拥有独立工作线程，也不能简单理解成“一启动就无限后台运行”；后台限制、前台服务规则和组件生命周期都会影响它。

对导出的 Service，重点看启动路径和绑定路径分别做了什么。Binder 方法应在执行敏感操作时确认调用者身份与权限；不能信任参数里自报的包名，也不能只在 UI 或某次 onCreate 中检查一次。

如果实现会调用 clearCallingIdentity，要确认权限判断发生在哪个身份下，并配对恢复身份。异步把任务交给其他线程后，再读“当前 Binder 调用者”也可能已经失去原始请求语境，因此要在入口取得并验证必要信息。

BroadcastReceiver：发送限制与接收限制分别看

发送敏感广播时，明确接收范围与所需权限；接收外部广播时，验证发送条件、参数与操作授权。只设置一个看起来难猜的 action，并不构成身份认证。

动态注册不能再统一写成“默认导出”。应按系统和 target SDK 使用相应标志；仅在进程内部传播状态时，可以使用普通回调或合适的可观察状态机制。LocalBroadcastManager 已弃用，旧项目分析时可以识别它，但不再作为新代码的默认建议。弃用说明

接收到空 extras、错误类型或超长字段时，应验证并拒绝不符合格式的输入。大范围 catch (Exception) 然后继续执行，并不能修好状态已经被部分修改的问题。

Content Provider：URI 权限、SQL 与文件路径是三道边界

检查 exported、readPermission、writePermission、path-permission 和 URI grant。exported=false 不表示所有被授予临时 URI 权限的外部访问都不可能发生；需要看应用是否主动授予了某条 URI 的访问能力。

查询接口里重点追 projection、selection、selectionArgs、sortOrder 与 URI 路由：

  • 数据值用占位符绑定，例如 owner_id = ? AND _id = ?。
  • 表名、列名、排序方向通常不能当作普通 SQL 值绑定，要映射到固定允许集合。
  • 参数化查询解决 SQL 语法注入，不自动解决调用者是否有权读取该行数据。

openFile 路径还要检查模式：只读 URI 是否能被请求为写入，目标是否落在允许目录，以及 URI grant 是否被扩大。可参考 Android SQL 注入说明。

默认设置：检查最终生效的配置

debuggable、备份和导出状态应从实际发布 APK 与设备行为确认。构建变体、依赖库 Manifest 合并和 OEM 行为都可能让源码里的意图与结果不同。

备份尤其不能只写一句 allowBackup=false 就结束。云备份与设备迁移的覆盖范围、dataExtractionRules/旧规则格式、系统版本需要分别记录；敏感凭据是否进入备份与恢复后是否还能被使用，是两个问题。Auto Backup 文档解释了这些条件。

网络：TLS、身份认证和授权分别验证

TLS 证书链与主机名校验解决“连到谁、传输是否被篡改”等问题。代码里空实现 checkServerTrusted、总返回 true 的 HostnameVerifier、或者在 onReceivedSslError 中直接 proceed()，都值得沿调用路径确认。

一般优先使用平台/网络库正确的默认校验，按需要配置可信 CA；调试证书放在调试配置里，避免把“临时抓包方便”的绕过带进 release。WebView 收到 SSL 错误时不应静默忽略并继续加载。Network Security Config提供了可声明的配置方式。

重放与幂等

仅加时间戳不能阻止窗口期内重放；签名如果没覆盖方法、路径、正文等关键字段，也可能被移用。根据协议需求，可以结合验证过的时间窗口、一次性 nonce、服务端去重记录和与请求内容绑定的认证。

幂等键与认证同样不同：前者控制重复执行，后者识别请求主体。检查时关注断网重试、App 重启、跨账户重用相同请求 ID 等情况。

Native Bridge 的额外权限

一个 WebView 中的脚本如果能调用读取私有文件、取 token 或执行设备操作的方法，就跨进了 App 的权限范围。现代系统仍需审查暴露方法和不可信内容可达性，不能因为用了 @JavascriptInterface 就认为业务授权已经解决。

旧系统上的反射类漏洞应单独注明 API 与 target 条件；现代 bridge 风险则更多需要沿“谁能加载页面—谁能执行脚本—哪些方法可调用”这条路径判断。Native Bridge 风险说明

签名、升级与敏感数据

META-INF/MANIFEST.MF、CERT.SF、CERT.RSA 属于 APK v1/JAR 签名体系，不能代表全部现代 APK 签名。核对签名时使用适合 APK 的验证工具，并记录实际签名方案与证书：

知道证书、公钥或证书指纹，不等于获得了用于签名的私钥。应用升级流程还要检查下载来源、文件替换时机与安装前后的签名身份关系。apksigner 文档

数据入口包括日志、外部存储、数据库、SharedPreferences、硬编码与网络传输。分析时再问一步：这些数据对哪个身份可读，生命周期多长，退出登录和备份恢复后是否仍可使用？

加密算法按用途看。散列不是加密，Base64 只是编码；把密钥和密文一起放进 APK 也不能依靠“加密过”获得秘密性。使用 AEAD 时要同时处理 nonce 唯一性、认证失败和密钥管理；Keystore 能提供相应密钥保护能力，但不能替代被允许调用解密功能时的业务授权。

ZIP 解压缩：路径越界只是一部分

ZIP entry 名称可以包含路径。危险逻辑通常是把它直接拼在目标目录后面就写文件。修复应验证规范化后的最终目标确实位于允许目录内，而不是只搜索字符串中有没有 ../。

目录边界要带分隔符，避免把 /safe-outside 当成 /safe 的子目录。示例还假定目标目录由应用控制；工程实现要处理符号链接、并发替换、覆盖策略、文件数量和解压后的大小限制。路径检查本身不解决 ZIP bomb。

Android 14 对 target 34+ 的部分 ZIP API 增加了相应路径检查，但这不覆盖所有自定义或第三方解压实现。版本保护和应用的目录策略仍需分别验证。Zip Path Traversal

怎样留下能复核的结果

每个发现记录 APK 哈希与版本、设备/API/target 信息、调用者身份、触发输入、实际输出和敏感操作。修复后同时复测应该拒绝的调用与合法功能，避免只证明“页面打不开了”。

原来的漏洞分类可以继续做索引，但结论最好写成一句可验证的话：哪个身份，经哪个入口，在什么条件下，访问或修改了什么。这样比把一串风险名勾完更容易定位真正的问题。
