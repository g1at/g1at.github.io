MQTT协议

分析 IoT、车机流量时，MQTT 很常见。端口连上以后能收到 JSON，并不代表已经看懂了协议：同一条消息为什么又来了，设备重连后为什么还能收到离线数据，刚订阅为什么立刻弹出一条旧状态，都要回到 MQTT 的会话与投递规则。

下面从客户端、Broker、Topic 和 QoS 讲到逐字节解析与本地实验。字节示例与实验均采用 MQTT 3.1.1，Broker 使用 Mosquitto 2.0.18；MQTT 5.0 的差异单独说明。

什么是 MQTT？

MQTT 是基于发布订阅模型的应用层消息协议。客户端可以既发布又订阅，Broker 负责接收连接、保存订阅并按主题转发消息。它通常建立在 TCP 上，使用 TLS 时提供传输加密和相应认证能力。

发布者与订阅者可以相互不知道地址，但两者都要与 Broker 建立连接。

MQTT 与 HTTP、XMPP 怎么比较

对持续上报遥测、下发控制消息的场景，MQTT 的主题路由和会话规则很方便。HTTP 则围绕请求、响应与资源语义展开，也能通过流式响应、SSE 等方式推送数据；重试和恢复同样可以在其上实现。选型时应比较应用需要维护的状态和交互模型，不能归纳成“HTTP 只能轮询”。

“MQTT 最小报文 2 字节”说的是 PINGREQ 等控制报文的协议长度，不包含 TCP/IP、TLS 和链路层开销。一个带主题、Packet Identifier 和 payload 的 PUBLISH 自然更长。它也不意味着 MQTT 会取代所有 XMPP 或 HTTP 应用。

MQTT 的工作原理

客户端与 Broker

一个简化的连接过程是：TCP 建连，客户端发 CONNECT，Broker 回 CONNACK，客户端再订阅或发布。认证结果、订阅是否成功、发布的投递确认分别处在不同步骤。

Client ID 是会话标识，不应被当作已经验证过的身份。 当另一个连接使用相同 Client ID 时，原连接会受到影响；认证与授权仍应由 Broker 的策略决定。分析“设备掉线”时也要排查 Client ID 冲突。

Topic Name 与 Topic Filter

发布使用 Topic Name；订阅使用 Topic Filter。两者大小写敏感，/ 划分层级，通配符只能出现在订阅过滤器里。

订阅过滤器 匹配例子 不匹配例子
sensor/+/temperature sensor/10/temperature sensor/10/room/temperature
sensor/# sensor、sensor/10/temperature sensors/10
+/status car/status car/1/status

+ 占一个完整层级；# 占剩余层级且必须位于末尾。空层级也有意义，例如 a//b 不能随手规范化成 a/b。此外，以 $ 开头的主题有特殊匹配规则，订阅 # 并不自动覆盖 $SYS/...。规则可对照 MQTT 3.1.1 的 Topic Names and Topic Filters。

QoS 保证到了哪一段

QoS 交换过程 接收端需要考虑什么
0 PUBLISH 没有协议级确认，消息可能丢失
1 PUBLISH → PUBACK 可能重复交付，需要考虑幂等
2 PUBLISH → PUBREC → PUBREL → PUBCOMP 协议在相应发送方与接收方之间处理一次交付语义

发布者到 Broker、Broker 到订阅者是两段独立投递。图中的箭头描述一段协议交换。

QoS 2 不是整个业务流程的“只执行一次事务”。设备收到命令后执行动作、写数据库、回结果，依然可能在应用崩溃或自身重试时遇到重复操作。带副作用的业务消息通常还需要 request_id、去重记录以及明确的过期策略。

订阅者实际收到的 QoS 还受原始发布等级和 Broker 授予的订阅等级约束。Packet Identifier 也有作用域和复用规则，不适合直接充当永久业务流水号。

一条 PUBLISH 到底长什么样

实验把 23.5 发布到 lab/temp，使用 QoS 1 并设置 RETAIN：

字节 含义
33 高四位 3 是 PUBLISH；DUP=0、QoS=1、RETAIN=1
10 Remaining Length=16，覆盖后面的可变头与 payload
00 08 主题的 UTF-8 编码占 8 字节
6c ... 70 lab/temp
00 01 本次 QoS 1 发布的 Packet Identifier=1
32 33 2e 35 应用负载 23.5

这里 MQTT 只把负载视为字节；它不会因为长得像数字就自动转换，也不会验证某个 JSON 字段是否有权执行。

Remaining Length 使用 base-128 变长编码，最多四个字节。它不是固定的一个字节：每字节低 7 位贡献数值，最高位表示是否还有后续字节。解析器既要限制长度字段本身，也要限制接受的消息大小，不能按对端声明无限分配内存。

Retained Message、Session 和 Will

这三个概念最容易被混到一起：

机制 保存/表达的是什么 典型用途
Retained Message 某个主题最后保存的保留消息 新订阅者立即得到当前状态
Persistent Session 与 Client ID 关联的订阅及协议规定的待交付状态 断线后恢复会话
Will Message 非正常断开等条件下由 Broker 发布的遗嘱消息 标记设备离线

保留消息不是历史消息列表。MQTT 3.1.1 中，向主题发布 RETAIN=1 且零长度 payload 的消息可清除该主题的保留消息；新订阅者随后不会再因这条已清除的记录收到旧值。

持久会话需要使用相同 Client ID，并设置 Clean Session=0。重连 CONNACK 中的 Session Present 帮助判断服务器是否恢复了已有会话。它与 Broker 是否把状态写入磁盘也不同：内存中的会话能支持连接重建，但 Broker 重启后能否恢复，还要看持久化配置。

MQTT 5.0 把这部分拆成 Clean Start 与 Session Expiry Interval，并提供 Message Expiry Interval 等属性。分析时先确认协议版本，再解释字段。参见 MQTT 5.0 标准。

从安全测试角度怎么读这些字段

在测试环境中，先建立两个权限不同的客户端账户，分别验证“能连接”“能订阅”“能收到”“能发布”“能引发操作”。成功 CONNECT 只能说明连接认证通过。

一个设备账户可以只读 devices/42/cmd、只写 devices/42/status。检查时既要试具体主题，也要试通配符、其他设备编号、保留消息读取以及持久会话恢复。ACL 的行为应以所用 Broker 版本与插件为准；Mosquitto 的主题访问规则见 配置手册。

应用端再核对命令是否绑定已认证身份，而不是相信 payload 里的 device_id。控制类主题尤其要考虑：旧 retained 命令会不会在设备上线时被再次执行？离线队列里的命令是否已经过期？收到重复 QoS 1 消息时是否重复开锁或重复写配置？这些问题要沿着实际业务流程验证，单看 TLS 和用户名密码还不够。
