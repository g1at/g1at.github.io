NNG协议

NNG 适合把线程、进程或不同机器上的模块用消息连接起来。真正写程序时，需要把协议语义、传输方式、连接角色、消息归属和异步操作的生命周期分开。

本文的 C 示例已在 Ubuntu 24.04、NNG 1.7.2 上编译并运行。NNG 是通信库，提供多种协议语义与 transport；正文讨论的是这套库的使用模型。可执行例子的环境是 1.7.2，消息所有权和 AIO 的链接采用当前 1.10 手册；复现其他版本时应再核对随安装包提供的头文件和手册。

概述：三个问题分开想

问题 对应概念 例子
消息怎样分发、收发顺序是什么 protocol REQ/REP、PUB/SUB、PUSH/PULL
字节从哪条通道过去 transport inproc://、ipc://、tcp://
谁主动建立连接 endpoint dialer、listener

NNG 的 brokerless 表示它不强制依赖独立 Broker，不表示项目不能自行增加转发节点。它与 MQTT 的主题会话服务器也不是同一种抽象，不能把“都能发布订阅”理解为它们具有相同的持久化、主题路由和投递保证。

通信协议

模式 消息行为 使用时要注意
PAIR 成对双向通信 具体连接数量与 pair 版本/选项有关
PUSH/PULL 一个 PUSH 将工作分发给可用 PULL 中的一方 适合任务分配，不是向所有工作者广播
PUB/SUB 向匹配的订阅方发送消息 慢订阅者、连接建立时机可能造成丢消息
REQ/REP 请求后等待回复 请求可能重发，有副作用时要处理幂等
BUS 向直接连接的其他节点发送 不等于自动构建任意多跳可靠广播网
SURVEY 一次询问收集多方回答 要定义响应窗口，不能无限等待所有节点

协议的状态限制也属于接口契约。以 cooked REQ 为例，尚未发送请求就接收会产生状态错误。要实现多个并发请求，可以使用协议支持的 nng_ctx，让每个上下文维护独立请求状态；原笔记中“没有 context”的说法不适用于这个层面。REQ 文档同时说明了重发与 context 行为。

重发不等于业务只执行一次

例如 REQ 发出 charge(order=42)，REP 已扣款，但回复丢失。协议重发请求之后，服务端如果再次扣款，就产生了业务重复。解决办法需要落到业务层：使用稳定的请求 ID，记录已处理结果，再对重复请求返回相同结果。

超时也不能证明远端没有执行。调用方只知道在自己的等待期限内没有收到最终回复，因此不能简单将一次超时等价为“安全重试”。

传输模式与连接角色

inproc:// 用于同一个进程中的 socket；ipc:// 用于本机进程间通信；tcp:// 用于 TCP 网络连接。换 URL 可以复用大量应用逻辑，但不是完全没有差异：不同 transport 的命名、权限、地址可达性和性能特征仍需考虑。

组合 PIPELINE 与 PUB/SUB

原笔记里的 PULL → PUB 转发方案仍然有用：多个生产者向一个汇聚节点 PUSH，汇聚节点用 PULL 接收后，再从 PUB 发给订阅者。

这里新增的是一个应用级转发节点，需要自己决定队列上限、慢消费者处理、重连后状态恢复以及关闭时如何收尾。它不会自动获得 MQTT 的 retained message 或持久 session。

NNG SUB 通常按消息开头的字节前缀过滤，也不是 MQTT 的 / 层级和 +/# 规则。例如自定义消息以 temperature/ 开头时，双方必须约定这个编码；如果把长度、类型或二进制头放在前面，过滤位置也随之改变。

数据传输：先把消息归属画清楚

使用 nng_sendmsg 时，最容易出错的是调用成功之后又去释放或修改同一条消息。

同步 nng_sendmsg 成功后，消息由库接管；失败则仍由调用者处理。对于接收得到的消息，应用最终应释放它，或者通过一次成功的消息发送把它交给库。nng_sendmsg 接口文档是核对这些规则的依据。

这里释放失败消息只是一个选择；如果准备重试，可以保留它，但必须避免其他线程同时修改。真正危险的是把同步与异步接口的成功时刻混用。

AIO：提交、完成、停止是三个阶段

异步 API 提交之后，结果由完成回调或 nng_aio_wait 等等待方式取得。此时不能把“提交函数已经返回”当作 I/O 已完成，也不能立即重用还在进行中的 nng_aio。

原笔记列出的 INIT_RECV、RECV_RET_SEND 等枚举，更适合被理解为应用自己定义的工作状态。它们不能替代库的完成结果。

回头读源码时看哪些地方

原来直接记函数调用链，换版本后很容易失效。更稳妥的阅读顺序是：

  1. 从公开头文件确定参数、返回值和所有权约定。
  2. 找对应协议的 socket/context 状态，确认允许的操作顺序。
  3. 跟进发送、接收队列，观察什么时候排队、取消、完成。
  4. 再看 transport 如何建立 pipe，以及断开连接怎样反馈。

公开的 nng_socket 是 opaque handle，不应靠猜测其内部是一个指针来设计自己的代码。阅读内部 nni_* 实现时也要固定版本；它们不是应用应依赖的稳定 API。

调试时留下哪些证据

收发日志至少记录业务请求 ID、协议角色、endpoint URL、消息长度、返回码与耗时。协议返回“超时”时，继续检查对端是否收到、是否已经处理、回复是否产生，再决定如何重试。

这能区分几类看起来相同的问题：连错 URL，SUB 前缀不匹配，REQ 状态错误，应用处理太慢，或者在发送完成之前就关闭了连接。单凭一句“NNG 没收到”很难继续排查。
